## Attacks attempted
- Cross-tenant relational integrity -> as authenticated user A, after confirming B's task was invisible, inserted A-owned rows referencing B-owned hidden parents. Actual successful `INSERT 0 1` results included `habit_completions(user_id=A, habit_id=B)`, `focus_sessions(user_id=A, task_id=B)`, `reminders(user_id=A, task_id=B)`, and `tasks(user_id=A, capture_id=B)`. Broke: single-column RLS protects row visibility but the FKs do not bind child `user_id` to parent ownership (`supabase/migrations/0001_initial_schema.sql:99-100`, `163-164`, `198-199`, `243-249`).
- Concurrent/offline LWW ordering -> inserted task value `newer edit` at `2026-07-11 12:00:00+00`, then performed the documented plain upsert with stale value `stale edit` at `11:00:00+00`. Actual final row: `title = stale edit`, `updated_at = 2026-07-11 11:00:00+00`. Broke: the documented plain-upsert algorithm (`docs/SCHEMA.md:62-66`) lets arrival order overwrite timestamp order, so it is not LWW.
- Inbox hot query -> populated 60,000 captures, disabled sequential scans to force inspection of `idx_captures_inbox`, and explained the documented multi-status query ordered by `captured_at DESC LIMIT 50`. Actual plan: `Bitmap Index Scan on idx_captures_inbox` -> `Bitmap Heap Scan` -> `Sort Key: captured_at DESC` -> `Limit`. Broke: `(user_id, status, captured_at DESC)` cannot provide global captured-time order across `status IN (...)`; the claim that it satisfies filter and sort (`docs/SCHEMA.md:172-175`) is false. With a 20,000-row one-user inbox distribution, the normal planner selected `Seq Scan` -> `Sort`.
- Semantic constraint attack -> inserted `focus_sessions(duration_minutes=-5, block_attempts=-2)`, `places(lat=999, lng=-999, radius_m=-10)`, `reminders(dwell_seconds=-60)`, and a `captures(status='pending', resulting_type='task', resulting_id=NULL)`. All returned `INSERT 0 1` and the invalid values. Broke: feature-critical numeric and state invariants are not enforced (`supabase/migrations/0001_initial_schema.sql:76-86`, `183-185`, `203-214`, `260-275`).
- Required feature coverage -> compared the P1 rubric and P9 deliverables to the task table. `tasks` contains `next_action` and `last_activity_at`, but no home for `stuck_since`/a stuck flag or `avoidance_reason` (`supabase/migrations/0001_initial_schema.sql:103-118`); `docs/SCHEMA.md:249-251` explicitly omits any goals table even though P9 requires minimal Goals (`SIDEKICK_BUILD_PLAN.md:417-423`). Broke: later features require a new schema migration before the supposedly locked schema can support them.
- Parent deletion semantics -> hard-deleted populated habit and task parents. Held for same-user data: habit completions/reminders cascaded, task reminders cascaded, and focus-session `task_id` became NULL, matching the documented intent.

## Findings
### BLOCKERS (must fix before Phase 2)
- [CRITICAL] Cross-user FKs are not tenant-safe - RLS checks only the child `user_id`, so an authenticated user can write relations to another user's invisible parent; parent deletion can then mutate/delete the other user's child row via FK actions - `supabase/migrations/0001_initial_schema.sql:99-100`, `163-164`, `198-199`, `228-229`, `243-259` - add parent `UNIQUE(id, user_id)` keys and composite child FKs `(parent_id, user_id)`, or equivalent ownership-enforcing constraints/triggers, then test every relationship dynamically.
- [CRITICAL] The documented sync algorithm is not last-write-wins - a later-arriving stale plain upsert overwrote a newer timestamped edit in the reproduced race - `docs/SCHEMA.md:53-66` - define and test a conditional server write (`excluded.updated_at > current.updated_at`) plus a deterministic equal-timestamp tie rule; reconsider client-clock skew and cursor semantics before P2 freezes the data contract.
- [HIGH] Required `dirty` and `synced_at` columns are absent from every syncable table - this intentionally deviates from the locked D5/P1 requirement and fails an explicit P1 rubric blocker - `SIDEKICK_BUILD_PLAN.md:23`, `SIDEKICK_BUILD_PLAN.md:214-215`, `supabase/migrations/0001_initial_schema.sql:11-15`, `docs/SCHEMA.md:23-49` - resolve the contract at the gate and make the locked schema/rationale unambiguous; if bookkeeping is local-only, the P1 contract and authoritative P2 mirror specification must be amended and approved rather than left as an open deviation.
- [HIGH] Phase coverage is incomplete - tasks have no persisted stuck marker/time or avoidance reason, and Goals has no storage at all, despite the rubric and P9 feature requirements - `supabase/migrations/0001_initial_schema.sql:103-118`, `docs/SCHEMA.md:237-251`, `SIDEKICK_BUILD_PLAN.md:417-423` - add the minimum fields/table needed by the frozen feature set or formally remove/defer those requirements before lock.
- [HIGH] The inbox index does not serve the documented hot query's order - multi-status filtering requires collecting matches and sorting before `LIMIT`; normal test distribution degraded to sequential scan - `supabase/migrations/0001_initial_schema.sql:303-306`, `docs/SCHEMA.md:172-175` - use an index matching the real inbox predicate/order (for example a suitable partial index led by `user_id, captured_at DESC`, depending on the final status predicate) and verify with representative `EXPLAIN (ANALYZE, BUFFERS)`.
- [HIGH] The schema accepts impossible feature states - negative session duration/attempt counts, invalid coordinates/radii/dwell, and contradictory capture triage state were all inserted successfully - `supabase/migrations/0001_initial_schema.sql:76-86`, `183-185`, `203-214`, `260-275` - add complete domain and cross-column CHECKs before downstream code relies on these invariants.
- [HIGH] The required source review and human lock are incomplete - `SIDEKICK_SPEC.md` is absent, the schema is explicitly proposed, inferred enum sets/open questions remain, and the checklist is unchecked; therefore screen/feature coverage and human acceptance cannot be reproduced - `SIDEKICK_BUILD_PLAN.md:194-206`, `SIDEKICK_BUILD_PLAN.md:240-257`, `docs/SCHEMA.md:3-19`, `docs/SCHEMA.md:212-268` - restore the source spec, resolve Q1-Q4, rerun coverage, record approval, and only then mark the migration locked.
- [MEDIUM] ERD exactness self-verification is false - audit columns are intentionally omitted and several nullable relationships are drawn as mandatory - `SIDEKICK_BUILD_PLAN.md:251`, `docs/ERD.md:3-7`, `docs/ERD.md:30-34`, `supabase/migrations/0001_initial_schema.sql:229`, `248-259` - correct nullability/cardinality and either show all columns or narrow the acceptance claim to an explicitly approved relationship-level ERD.
- [MEDIUM] The official verification command is not portable to the current review environment - `bash scripts/test_migration.sh` exits before starting Docker even though Docker is available; a reviewer/CI host without bash cannot reproduce the advertised command - `docs/SCHEMA.md:7-10`, `scripts/test_migration.sh:1-31` - add a PowerShell/portable wrapper or document and provision the required runtime. The underlying database steps did pass when reproduced manually.
